# Автономная установка Mikro-Clear на SELKS

Дата: 2026-07-24

Статус: дизайн утверждён

## Контекст

Текущая инструкция `docs/ru/install-from-github.md` описывает обновление уже
подготовленного SELKS с управляющей рабочей станции. Она предполагает готовые
`/opt/mikroclear-venv`, `/etc/mikroclear/mikroclear.env`, systemd unit,
SSH alias и отдельную передачу wheel-артефакта. Поэтому по ней нельзя
воспроизводимо установить Mikro-Clear на чистую систему.

Новая установка должна выполняться непосредственно на целевом SELKS из
локально клонированного Git checkout. Установщик не обращается к управляющей
рабочей станции, не выполняет SSH-оркестрацию и не использует MCP-компоненты.

## Цели

- Дать оператору полную русскую инструкцию установки с нуля.
- Добавить один операторский entrypoint `scripts/install-selks.sh`.
- Поддержать интерактивную настройку и безопасную установку с шаблоном
  конфигурации.
- Запускать runtime от отдельного системного пользователя `mikroclear`.
- Безопасно повторять установку для обновления.
- Автоматически откатывать неуспешное обновление к предыдущему рабочему
  состоянию.
- Зафиксировать воспроизводимый план тестирования на Debian 12 и 13.

## Не входит в задачу

- Удалённая установка по SSH с другой машины.
- Изменение прав, владельцев или Docker-конфигурации SELKS ради доступа к
  `eve.json`.
- Автоматическое обновление Git checkout.
- Автоматическая установка системных пакетов не через `apt-get`.
- Обращение автоматических тестов к production RouterOS или Telegram.
- Полноценный универсальный package manager для всех дистрибутивов Linux.

## Источник устанавливаемого кода

Оператор самостоятельно клонирует репозиторий на целевую машину и выбирает
нужную ветку, tag или commit. Установщик ставит только текущий committed
`HEAD`.

Перед сборкой установщик:

1. проверяет, что каталог является Git checkout;
2. определяет полный commit SHA;
3. создаёт чистый исходный snapshot через `git archive HEAD`;
4. строит wheel из snapshot, а не из рабочей директории;
5. записывает commit SHA и SHA-256 wheel в install manifest.

Незакоммиченные и неотслеживаемые файлы не попадают в артефакт. Установщик
никогда не выполняет `git pull`, `git fetch`, checkout или переключение ветки.

## Поддерживаемая платформа

Официальная тестовая матрица:

- Debian 12;
- Debian 13.

Новые версии Debian разрешены. Другие Linux-дистрибутивы разрешены при наличии:

- systemd;
- Python 3.11 или новее;
- модуля `venv` и `pip`;
- Git;
- `install`;
- `sha256sum`;
- OpenSSL;
- стандартных GNU/coreutils-инструментов, используемых скриптом.

Жёсткой проверки имени или версии дистрибутива нет. Проверяются фактические
возможности системы.

Если отсутствуют системные зависимости и доступен `apt-get`, установщик
показывает точный список пакетов и запрашивает подтверждение установки. Без
подтверждения состояние системы не меняется. Если `apt-get` отсутствует,
установщик продолжает работу при наличии всех необходимых команд, а иначе
завершается со списком недостающих компонентов и не пытается использовать
другой package manager.

Для получения Python-пакетов нужен доступ к настроенному Python package index
либо предварительно заполненный локальный cache.

## Интерфейс установщика

Установщик запускается от `root` из корня Git checkout:

```bash
./scripts/install-selks.sh
```

Без флагов в интерактивном терминале он предлагает выбрать один из режимов:

1. интерактивная настройка;
2. установка с шаблоном конфигурации.

Для автоматизации доступны:

```bash
./scripts/install-selks.sh --interactive
./scripts/install-selks.sh --config-template
./scripts/install-selks.sh --start
./scripts/install-selks.sh --help
```

`--interactive` создаёт или целенаправленно перенастраивает конфигурацию,
устанавливает компоненты, запускает сервис и выполняет acceptance.

`--config-template` устанавливает компоненты и создаёт шаблон конфигурации, но
не запускает сервис. После заполнения шаблона оператор выполняет `--start`.
Этот режим предназначен для чистой установки. Если обнаружена уже настроенная
установка, существующий env-файл и работающий сервис остаются без изменений, а
установщик предлагает использовать обычное обновление или `--interactive`.

`--start` не пересобирает конфигурацию: он проверяет существующий env-файл,
права, сертификат и доступность runtime-путей, затем запускает сервис и
выполняет acceptance.

Повторный обычный запуск считается обновлением. Существующая конфигурация не
перезаписывается без явно выбранного интерактивного перенастроения.

## Предварительные проверки

До первой мутации установщик проверяет:

- effective UID равен `0`;
- система использует systemd;
- доступен Python 3.11+ и рабочий `venv`;
- доступны Git, OpenSSL, `install`, `sha256sum` и `flock`;
- Git `HEAD` существует и может быть архивирован;
- пути установки не конфликтуют с обычными файлами или неожиданными symlink;
- доступно достаточно места для сборки и резервной копии;
- другой экземпляр установщика не удерживает lock.

Для сериализации запусков используется `flock`. При занятом lock второй
экземпляр завершается без изменений и сообщает PID или путь lock-файла.

## Пользователь, каталоги и права

Установщик создаёт системные группу и пользователя `mikroclear` без login shell
и домашнего каталога.

Целевые пути:

| Путь | Владелец и режим | Назначение |
| --- | --- | --- |
| `/opt/mikroclear-venv` | `root:root`, без записи для runtime | Python venv |
| `/etc/mikroclear` | `root:mikroclear`, `0750` | конфигурация |
| `/etc/mikroclear/mikroclear.env` | `root:mikroclear`, `0640` | переменные runtime |
| `/etc/mikroclear/certs` | `root:mikroclear`, `0750` | доверенные сертификаты |
| `/etc/mikroclear/certs/mikrotik-ca.crt` | `root:mikroclear`, `0640` | CA RouterOS |
| `/var/lib/mikroclear` | `mikroclear:mikroclear`, `0700` | изменяемое состояние |
| `/var/backups/mikroclear` | `root:root`, `0700` | rollback-наборы |
| `/etc/systemd/system/mikroclear.service` | `root:root`, `0644` | systemd unit |

Новая установка нигде не зависит от каталога сертификатов другого сервиса.
Путь CA по умолчанию в Python settings, env-примере, тестах и документации
меняется на `/etc/mikroclear/certs/mikrotik-ca.crt`.

## Доступ к Suricata EVE

До запуска выполняется фактическая проверка от пользователя runtime:

```bash
sudo -u mikroclear test -r /opt/SELKS/docker/containers-data/suricata/logs/eve.json
```

Также проверяется traversal каждого родительского каталога. Если файл
недоступен, установщик:

1. не меняет владельца, группу, ACL или режимы SELKS/Docker;
2. показывает текущие `namei`/`stat`-данные;
3. формирует точную команду исправления для оператора с учётом найденной
   группы или ACL;
4. завершает работу до запуска сервиса.

После ручного исправления оператор повторно запускает установщик или `--start`.

## Сборка и Python-зависимости

Wheel собирается во временном каталоге из `git archive HEAD` и проходит
существующую проверку `scripts/validate_wheel_artifact.py`.

Production venv содержит только runtime-пакет и его runtime-зависимости.
`requirements.txt` и optional/tooling extras установщиком не используются.
Пакет `mcp` не входит в `[project].dependencies`; при необходимости инструментам
репозитория он может предоставляться только отдельной optional dependency
group, которая не устанавливается production-сценарием.

Перед переключением версии сохраняются:

- точная файловая копия предыдущего production venv, включая runtime-пакет и
  зависимости;
- предыдущий wheel, если он был сохранён прошлым запуском установщика;
- список установленных Python-пакетов и их версий;
- текущий unit;
- env-файл;
- CA-файл;
- install manifest.

Установка wheel считается успешной только после импорта `mikroclear` из
`site-packages` при `WorkingDirectory=/`.

## Конфигурация

### Режим шаблона

Установщик атомарно создаёт `/etc/mikroclear/mikroclear.env` с комментариями и
пустыми обязательными значениями. Файл получает `root:mikroclear` и `0640`.
Сервис остаётся disabled/stopped до заполнения и отдельного `--start`.

Если env-файл уже существует, режим не перезаписывает его и сообщает, как
запустить интерактивное перенастроение.

### Интерактивный режим

Обязательные значения:

- адрес или имя RouterOS;
- пользователь RouterOS;
- пароль RouterOS, вводимый без echo;
- порт;
- режим TLS.

Для проверяемого TLS оператор указывает исходный CA-файл. Установщик проверяет
его через OpenSSL и копирует в
`/etc/mikroclear/certs/mikrotik-ca.crt`. Отключение проверки сертификата
доступно только как явный небезопасный выбор с предупреждением.

Telegram настраивается опционально. Token вводится без echo. Mangle control по
умолчанию выключен и включается только явным выбором.

Перед записью показывается сводка. Пароли, token и другие секреты заменяются
маской. Env записывается во временный файл в том же каталоге, проверяется и
атомарно переименовывается. Секреты не передаются через аргументы командной
строки и не выводятся в журнал установщика.

## Systemd unit

Unit запускает:

```text
/opt/mikroclear-venv/bin/python -m mikroclear
```

Обязательные свойства:

- `User=mikroclear`;
- `Group=mikroclear`;
- `WorkingDirectory=/`;
- `EnvironmentFile=/etc/mikroclear/mikroclear.env`;
- `Restart=on-failure`;
- запись разрешена только в `/var/lib/mikroclear`;
- чтение разрешено для `/etc/mikroclear` и Suricata EVE path;
- существующие безопасные systemd hardening-настройки сохраняются, если они
  совместимы с non-root runtime.

До установки unit проверяется через `systemd-analyze verify`. После установки
выполняется `systemctl daemon-reload`.

## Чистая установка

На чистой системе порядок такой:

1. preflight и предложение установить отсутствующие apt-зависимости;
2. получение lock;
3. создание чистого source snapshot и wheel;
4. создание пользователя и каталогов;
5. создание production venv и установка runtime wheel;
6. интерактивная конфигурация либо безопасный шаблон;
7. установка и проверка systemd unit;
8. проверки чтения EVE, чтения конфигурации и записи state от `mikroclear`;
9. запуск только для полностью настроенного режима;
10. acceptance.

При ошибке чистой установки созданные файлы сохраняются для диагностики,
сервис останавливается, а установщик возвращает ненулевой код. Он показывает
безопасные команды `systemctl status`, `journalctl` и проверки прав, не
раскрывающие env-секреты.

## Обновление и rollback

До изменения рабочей установки создаётся каталог:

```text
/var/backups/mikroclear/<UTC timestamp>/
```

Он содержит предыдущие package-артефакты, unit, env, CA и manifest с commit/SHA.
Новая конфигурация не заменяет старую, если оператор явно не выбрал
перенастроение.

Production venv сначала подготавливается и проверяется как кандидат. Замена
рабочего venv выполняется только после успешной сборки и сохранения его точной
файловой копии. Поэтому изменение набора или версий зависимостей также
откатывается, а не остаётся после возврата старого wheel.

После установки новой версии выполняется acceptance. При неуспехе установщик:

1. останавливает неуспешную версию;
2. восстанавливает точную копию предыдущего venv, unit, env, CA и manifest;
3. выполняет `systemctl daemon-reload`;
4. запускает предыдущую версию;
5. повторяет минимальную health-проверку rollback;
6. возвращает ненулевой код и показывает путь backup.

Rollback считается успешным только если предыдущий сервис снова
`active/running`. Неуспех rollback выделяется отдельным сообщением и кодом,
чтобы не создать ложное впечатление о восстановлении.

## Acceptance

Тайм-аут по умолчанию — 90 секунд. Установщик проверяет:

- импорт `mikroclear` из production `site-packages`;
- `User=mikroclear`, `Group=mikroclear` и `WorkingDirectory=/` в unit;
- `ActiveState=active`, `SubState=running`;
- `NRestarts=0` на интервале наблюдения;
- процесс действительно работает от `mikroclear`;
- `eve.json` читается от `mikroclear`;
- `/var/lib/mikroclear` доступен для записи от `mikroclear`;
- runtime подтвердил подключение к RouterOS;
- в журнале нет traceback или fatal marker после текущего запуска;
- при включённом Telegram запущен дополнительный worker и есть marker его
  запуска;
- при выключенном Telegram дополнительный worker не требуется.

После успешного acceptance оператору показываются commit SHA, SHA-256 wheel,
версия Python, статус сервиса и команды дальнейшей проверки, включая Telegram
`/status`.

## Тестируемость установщика

`scripts/install-selks.sh` остаётся единственным операторским entrypoint, но
организуется как набор функций с guard на прямой запуск. Автоматические тесты
могут source-ить функции без запуска установки.

Тестовый режим разрешает перенаправить целевые пути в созданный тестом
временный root. Он включается только отдельным test-mode признаком и не
документируется как production-возможность. Production-запуск не принимает
произвольный root prefix.

Python `unittest` запускает Bash-функции в subprocess. Новая обязательная
зависимость Bats не вводится.

## Автоматические проверки

- `bash -n scripts/install-selks.sh`;
- ShellCheck установщика;
- unit-тесты разбора аргументов и выбора двух режимов;
- тест отсутствующих зависимостей с apt и без apt;
- тест отсутствия мутаций до успешного preflight;
- тест атомарной записи env и маскировки секретов;
- тест отказа при нечитаемом EVE без chmod/chown/setfacl;
- тест идемпотентного повторного запуска;
- тест успешного обновления;
- тест искусственно неуспешного acceptance и rollback;
- тест отказа запуска неполного шаблона;
- проверка unit на `User/Group=mikroclear` и `WorkingDirectory=/`;
- установка wheel в чистый временный venv с подтверждением отсутствия пакета
  `mcp`;
- repository scan, запрещающий старый путь CA в новом installer/runtime/docs
  контуре;
- focused tests, полный `unittest discover`, `compileall` и `git diff --check`.

Live Telegram и RouterOS не вызываются автоматическими тестами. Их границы
заменяются локальными doubles.

## Интеграционная и воспроизводимая проверка

На чистых VM со snapshot выполняются:

1. template install на Debian 12;
2. interactive install на Debian 12;
3. template install на Debian 13;
4. interactive install на Debian 13;
5. smoke test на более новой Debian;
6. система без apt при наличии всех prerequisite;
7. система без apt с недостающим prerequisite;
8. отказ доступа к EVE;
9. повторный idempotent запуск;
10. успешное обновление;
11. неуспешное обновление и подтверждённый rollback;
12. Telegram disabled acceptance;
13. Telegram enabled acceptance на отдельном тестовом bot;
14. ручная установка по документации без установочного скрипта.

Для каждого прогона сохраняются:

- версия ОС;
- версия Python;
- commit SHA и SHA-256 wheel;
- выбранный режим;
- установленные пути и права;
- вывод machine-readable systemd status;
- итог acceptance или rollback;
- подтверждение отсутствия секретов в сохранённых логах.

Точные команды подготовки VM, выполнения сценариев, ожидаемые результаты и
возврат к чистому snapshot фиксируются в
`docs/ru/install-test-reproduction.md`.

## Критерии приёмки реализации

- Чистая установка выполняется непосредственно на SELKS после `git clone`.
- Оператор выбирает интерактивный режим или режим шаблона.
- Сервис запускается от `mikroclear`, а не от `root`.
- Новая установка использует только
  `/etc/mikroclear/certs/mikrotik-ca.crt`.
- Production venv не содержит пакет `mcp`.
- Установщик не обновляет Git checkout и ставит точный committed `HEAD`.
- Нечитаемый EVE останавливает запуск без изменения SELKS/Docker permissions.
- Повторный запуск сохраняет действующую конфигурацию.
- Неуспешное обновление восстанавливает предыдущую рабочую версию.
- Debian 12 и 13 проходят документированную тестовую матрицу.
- Полный ручной сценарий и автоматический сценарий описаны на русском языке.
